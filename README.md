# 우리집 자산 대시보드 (Asset Dashboard)

부부가 함께 쓰는 **로컬 우선** 자산관리 · 가계부 웹앱입니다.
매달 번 돈과 쓴 돈을 구성원(남편/아내)별로 기록하고, 순자산이 어떻게
쌓이는지 그래프로 확인합니다.

## 특징

- 🖥️ **로컬 우선** — 서버·회원가입 없이 내 PC 브라우저에서 실행. 데이터는
  브라우저(IndexedDB)에 영구 저장됩니다.
- 👫 **구성원 구분** — 모든 수입/지출을 남편·아내로 구분해 입력하고,
  각각 또는 합산으로 조회.
- 📊 **대시보드 그래프** — 이번 달 수입/지출/저축률, 최근 6개월 추이,
  카테고리별 지출, 구성원별 비교, 누적 저축 추이.
- 🎯 **예산 관리** — 카테고리별 월 예산을 정하고, 실제 지출 대비 소진율을
  진행 바로 확인. 초과 시 빨간색 경고.
- 🔁 **반복 거래** — 월급·구독료처럼 매월 반복되는 항목을 등록하면 앱을 열 때
  밀린 달까지 자동으로 기록(중복 없음).
- 📥 **CSV 가져오기** — 은행·카드사 CSV를 불러와 거래로 일괄 등록. EUC-KR 자동
  감지, 입금/출금 분리 컬럼, 다양한 날짜 형식 지원. 컬럼 연결 → 미리보기 → 가져오기.
- 🔎 **적요 자동 분류** — 거래 내용(적요) 키워드로 카테고리 자동 배정(예: 스타벅스
  → 식비). 기본 규칙 내장, 설정에서 규칙 추가·수정 가능.
- 💰 **자산 현황** — 월별 계좌 잔액을 입력해 순자산(투자·예금 포함) 추이 기록.
- 💾 **백업** — JSON 내보내기/가져오기로 백업하거나 다른 PC로 이전.

## 실행 방법

Node.js 18+ 가 필요합니다.

```bash
npm install      # 최초 1회
npm run dev      # 개발 서버 실행 → 자동으로 브라우저 열림 (http://localhost:5173)
```

배포 없이 그냥 이대로 쓰면 됩니다. 다른 사람과 공유되지 않고 이 PC에만
저장됩니다.

### 프로덕션 빌드 (선택)

```bash
npm run build    # dist/ 폴더 생성
npm run preview  # 빌드 결과 미리보기
```

## 설계 개요

### 핵심 개념: 현금 흐름 ↔ 자산 잔액 분리

- **현금 흐름 (거래 입력)** — 언제/누가/얼마를 벌고 썼는지의 개별 내역.
- **자산 잔액 (자산 현황)** — 매월 말 계좌별 잔고 스냅샷. 투자 평가액은
  거래 없이도 오르내리므로, 순자산 추이는 이 스냅샷으로 그립니다.

### 데이터 모델

| 테이블 | 필드 |
|--------|------|
| `members` | name, color |
| `categories` | name, kind(수입/지출), color |
| `accounts` | name, type(현금/예금/적금/투자/부동산/부채), owner |
| `transactions` | date, kind, amount, memberId, categoryId, accountId, memo |
| `snapshots` | month, accountId, balance |
| `budgets` | categoryId, amount(월 예산 한도) |
| `recurring` | memo, kind, amount, memberId, categoryId, dayOfMonth, startMonth, active, lastPostedMonth |
| `catRules` | keyword, categoryId (적요 키워드 자동 분류) |

### 기술 스택

- **Vite + React + TypeScript** — 가벼운 SPA
- **Dexie (IndexedDB)** — 브라우저 로컬 DB, 네이티브 모듈 불필요
- **Recharts** — 차트
- **react-router-dom** — 페이지 라우팅

## 클라우드 동기화 검토 (지금은 미적용)

현재는 데이터가 **각 브라우저의 IndexedDB 안**에만 있어 기기 간 공유가 되지
않습니다. 여러 기기에서 같은 데이터를 보려면 두 기기 사이에 **공용 서버**가
필요합니다. 부부 둘이 쓰기에는 로컬 우선 + JSON 백업으로 충분하며, 자산·소비
내역이 외부로 나가지 않아 프라이버시에도 유리합니다.

### 언제 도입을 검토할까 (결정 포인트)

아래가 불편해지는 시점이 도입 신호입니다.

1. **여러 기기에서 동시에 입력**할 일이 잦아진다 — 부부가 각자 폰으로 그때그때
   지출을 기록하고 싶다.
2. **폰에서 편하게 접속**하고 싶다 — 그러면 URL 배포가 사실상 필수라, 로컬
   `npm run dev` 실행만으로는 한계가 온다.
3. **금융 데이터를 외부 서버에 올리는 것이 괜찮다** — 자산·소비 내역이 기기를
   떠나 서버에 저장되는 것을 수용할 수 있다.

1·2번이 불편해지고 3번이 괜찮다면 도입할 때입니다.

### 도입 시 필요한 것 (6가지)

| # | 구성요소 | 이유 |
|---|----------|------|
| 1 | 서버 DB | 브라우저 밖에 데이터가 있어야 여러 기기가 같은 걸 봄 |
| 2 | 로그인(인증) | 아무나 못 보게. 부부 2명 계정 |
| 3 | 접근 권한 규칙 | 로그인한 사람은 "자기 가구 데이터만" 읽고 쓰게 제한 |
| 4 | 동기화 로직 | 서버와 읽고 쓰기 + 실시간 반영 + 충돌 처리 |
| 5 | 호스팅/배포 | `npm run dev`가 아니라 URL 접속 (폰 사용 시 필수) |
| 6 | 시크릿 관리 | API 키·접속 정보 |

데이터 모델도 한 층 늘어납니다: 기존 `members`(소비 주체) 위에 **로그인 계정**과
두 계정을 묶는 **가구(household)** 개념이 추가되고, 모든 레코드에 `household_id`가
붙어 "내 가구 것만" 권한 규칙이 강제됩니다.

### 현실적인 선택지 2개

- **Dexie Cloud** — 지금 Dexie 코드를 거의 그대로 두고 동기화만 얹음. 오프라인
  유지(로컬 우선 철학과 가장 잘 맞음), 부부 2명은 무료권. **변경 최소**.
- **Supabase** — Postgres + 인증 + 권한규칙(RLS) + 실시간. 데이터 계층을 교체하고
  로그인 화면을 추가해야 하지만 **완전한 제어·확장성**. 무료 티어로 충분.

> 어느 쪽이든 현재 스키마와 백업 JSON 구조를 그대로 이어받도록 설계되어 있어,
> 그동안 쌓인 데이터를 잃지 않고 옮길 수 있습니다. 계정 생성·키 발급 등 초기
> 셋업의 일부는 본인이 직접 해야 합니다(비밀키는 본인 소유).
